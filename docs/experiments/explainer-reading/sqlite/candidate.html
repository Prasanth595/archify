为什么 SQLite 能边读边写，长读却拖慢回写？

长图

答

结论

WAL 让读者保留开始时的快照，同时让写者追加新内容；检查点回写数据库时却要保护旧快照。长读可能让回写停在中途，持续写入时 WAL 可能增长。1

  1. 同一时刻只有一个写事务。1
  2. 回写完成和 WAL 文件缩小是不同的事。1

适用于SQLite WAL 模式单个数据库位置为示意

1

为什么读者和写者可以同时工作？

图的结构
  • 读事务 reader
  • 数据库文件 database
  • WAL 日志 log
  • 写事务 writer
  • reader → database
  • reader → log
  • writer → log

读事务开始时记住最后一次提交的位置，SQLite 称它为结束标记。事务期间，这个位置不变。1

  1. WAL 日志 ↗

    读者查找不晚于结束标记的最新页。

  2. 数据库文件 ↗

    WAL 没有该页时，读者从数据库文件读取。

  3. 写事务 ↗

    写者向 WAL 追加新页，不改变读者快照。

2

长读如何限制回写？

图的结构
  • 读者固定快照 snapshot
  • 写者追加提交 append
  • 检查点回写 checkpoint
  • 遇到读者边界 boundary
  • append → checkpoint · 随后
  • checkpoint → boundary · 停在此处
  • snapshot → append · 期间

假设读者固定在提交 A，随后写者提交 B。检查点可以回写安全的部分，但不能越过该读者的结束标记。否则它可能覆盖数据库文件中读者仍需读取的页。1

停顿不等于写入停止

后续写入仍可追加；如果一直有旧读者，检查点可能无法完成，WAL 也可能增长。只有旧读者结束并且检查点再次运行后，才有机会继续推进。1

3

检查点完成后，文件会立刻缩小吗？

不一定。检查点回写和 WAL 重置或截断是不同步骤。读者结束使用 WAL 后，SQLite 才能在合适时机从头复用它；文件大小本身不等于尚未回写的数据量。1

模式等待与结果
PASSIVE不等待读者或写者，尽量回写；可能未完成。
FULL等待写者和旧快照，运行时阻挡并发写者；等待可能失败。
RESTART在 FULL 基础上等待所有读者结束使用 WAL，成功后下次写入可从头复用。
TRUNCATE在 RESTART 基础上，成功时将 WAL 截为零字节。

FULL、RESTART 和 TRUNCATE 的等待受 busy handler 限制；若它停止等待，操作可能返回 SQLITE_BUSY，只完成部分回写。23
