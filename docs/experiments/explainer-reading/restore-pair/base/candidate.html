git restore 到底改了哪里？

长图

答

结论

先看目标，再看来源：默认只改工作区，并从暂存区取内容；加上 --staged 后，默认从 HEAD 取内容并改暂存区。--source 可以明确指定来源。1

  1. --staged 和 --worktree 决定写入哪里；两者都写时，两个位置都会被更新。1
  2. 没有 --source 时，只要指定了 --staged，默认来源就是 HEAD。1
  3. 覆盖工作区或暂存区前，先检查并保存需要保留的修改。1

适用于单个已跟踪文件非冲突状态HEAD 已存在

1

三份内容如何流动？

HEAD 是当前提交；暂存区是下一次提交的候选内容；工作区是磁盘上编辑的文件。下面的箭头表示可选来源和目标，不表示一次命令会走完所有箭头。

图的结构
  • HEAD head
  • 暂存区 index
  • 工作区 worktree
  • head → index · --staged
  • index → worktree · 默认
  • head → worktree · --source=HEAD

这些操作不会移动 HEAD 或创建提交。命令后面的 -- file 限定本例作用于这个文件。1

2

四种写法分别复制什么？

假设文件在 HEAD 和暂存区中都存在，且各处内容可以不同。每行独立执行，未列为目标的位置保持不变。1

命令来源写入目标保持不变
git restore -- file暂存区工作区暂存区、HEAD
git restore --staged -- fileHEAD暂存区工作区、HEAD
git restore --source=HEAD -- fileHEAD工作区暂存区、HEAD
git restore --staged --worktree -- fileHEAD暂存区和工作区HEAD

最后一行也可写成 git restore --source=HEAD --staged --worktree -- file。显式来源让意图更容易看懂。1

3

哪些修改可能丢失？

目标位置会被覆盖

写入工作区会丢弃该文件现有的未暂存修改；写入暂存区会替换已暂存内容。先备份或提交需要保留的内容。

如果已跟踪路径在所选来源中不存在，默认模式会删除目标中的该路径，以匹配来源。--overlay 可避免删除。1

冲突文件不适用上表的简单复制模型。从暂存区恢复工作区时，未合并条目需要相应的冲突选项处理。稀疏检出和子模块也有额外规则。1
