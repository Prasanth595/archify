# Document presentation

Read this for styled Markdown documents, rendered answers, or local diagram
components inside a document. Use ordinary Markdown and the existing document
renderer. Any supplied HTML can provide the design; it owns its styles, layout,
components and scripts.

If its calculations need inputs absent from the Markdown, report the concrete
render diagnostic or adapt the HTML within the user's editing scope. Preserve
the authored content and do not fabricate inputs to make a diagram appear.

## Select a presentation

Honor the user's HTML when supplied. Otherwise choose a report family for the
requested purpose and arrange the Markdown accordingly:

| Family | Intended reading | Useful authoring choices |
| --- | --- | --- |
| `decision` | Understand the recommendation, alternatives and supporting conditions | Lead with the recommendation; place alternatives and their stated conditions together; finish with the next action |
| `analysis` | Follow an investigation, evidence and explanation | Keep observations beside their sources; group related objects or measurements; retain code and limitations where they are discussed |
| `review` | Follow a retrospective, differences and subsequent work | Use the authored order of events or steps; state observations, changes and follow-up actions explicitly; supply dates when a time scale is intended |

Each has `/static` and `/dynamic` variants. These are six ordinary HTML designs,
not rules for interpreting arbitrary sentences. Use the variant requested by the
user; `review/static` is the renderer's default when no design is selected.
Existing numerical, date, list and text-structure figures remain available in
these designs. Supply actual values and units for measurements.

## Render through the existing tool

When `render_markdown` is available, provide exactly one of `markdown` and
`markdown_path`, one design source, and `output_path`. Choose `design_path` for a
supplied HTML file or `template` for a built-in ID. The tool also accepts any
HTML design by URL and saved HTML templates; use its advertised input schema.

```json
{
  "markdown_path": "/path/report.md",
  "template": "review/static",
  "output_path": "/path/report.html"
}
```

With shell access, call the same renderer from the selected Archify package:

```sh
node /path/archify/bin/archify.mjs document report.md report.html --template analysis/dynamic --json
node /path/archify/bin/archify.mjs document report.md report.html --design design.html --json
```

The JSON entry point is `node /path/archify/bin/document-tool.mjs request.json`.
Replace `/path/archify` with the actual package path. Local Chrome is required.
No agent installation or client configuration is needed for the command line.

## Optional native document components

Components also run through this renderer. The Skill chooses an existing
component and marks its source paragraphs; the chosen HTML reads those marks
after Markdown is mapped. Do not assemble a second output page or manually draw
SVG as a substitute for the rendering call.

Use components when an explicit local relationship, grouping or sequence would
help the document. The author chooses that relationship by selecting the
component; the renderer does not discover it from keywords. The supplied native
component design is `document/designs/components/native.html` within the package.
It reuses SVG generated by Archify's original Architecture, Workflow, Tree and
Lifecycle renderers, with their node shapes, symbols, regions and paths.

Select this HTML with `design_path`, or:

```sh
node /path/archify/bin/archify.mjs document report.md report.html --design /path/archify/document/designs/components/native.html --json
```

Component marks are opt-in rendering instructions supported by that HTML.
The six report layouts continue to accept ordinary Markdown; adding these marks
to an HTML design that does not implement them does not activate components.
The component design is an additional HTML input, not a seventh built-in ID.

### Mark an instance and its positions

```md
## [g1:regions] This section's title

[g1.1.1] **Input.** Keep the source material and conditions together.

[g1.2.1] **Check.** Repeat the work under the same conditions.

[g1.2.2] **Deliver.** Preserve the result and its stated limitations.
```

`g1` identifies this section's component instance; `regions` chooses the preset.
`g1.2.1` puts the whole paragraph into region 2, position 1. Region and position
mean what that preset defines; they are rendering addresses, not inferred
content roles. Use stable component names rather than catalogue ordinals.

| Component | Addressed positions | Presentation |
| --- | --- | --- |
| `regions` | `1.1`; `2.1`, `2.2` | One node in the first region; two connected nodes in the second |
| `converge` | `1.1`, `1.2`; `2.1` | Two nodes connect to one node |
| `branch` | `0.1`, `0.2`, `0.3`; `1.2` | Three ordered main nodes; a branch from the second |
| `lanes` | `1.1`, `2.2`, `1.3`, `2.4` | Four ordered steps across two regions |
| `decompose` | `0.1`; `1.1`, `1.2`; `2.1`–`2.4` | One node expands to two, then four |
| `return` | `0.1`, `0.2`, `0.3`; `1.2` | Main path, return to the first node, and a wait branch at the second |

Use one component per H2 section and provide its listed positions. The address
belongs at the beginning of a paragraph. A normal newline continues that same
paragraph; it needs no extra mark. Repeated addresses append paragraphs to the
same position in source order. Unmarked paragraphs remain in the document flow.
Bold, links and inline code keep their Markdown form.

These native presets have fixed position counts and content capacity. Keep
`return` nodes concise; its original stage shapes are compact. Unsupported or
incomplete marks and paragraphs that do not fit retain readable source content
with a notice. Review that notice and choose a suitable preset or retain prose;
do not silently shorten or discard the user's text.

The complete input example is
[native-components.md](../document/designs/examples/native-components.md).
The component design and its marks do not alter the general Markdown parser or
require other HTML designs to adopt this syntax.

## Return the actual result

Require `ok: true` and a saved output path and checksum. Inspect meaningful
component notices and, when appearance matters, the rendered page. Initialization
checks verify mapped content and script errors, not every later interaction.
Return the actual HTML and what was checked. The native diagram `finalize`
workflow applies to standalone typed diagrams; this document path uses the
document renderer's own report.
