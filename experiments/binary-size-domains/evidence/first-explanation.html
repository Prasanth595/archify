文件只有 16,888 B，total 为何超过 4 GiB？

长图

答

结论

zero-1m 的文件只有 16,888 B。size -m 的 total 包含不可访问的 4 GiB PAGEZERO，不能当成实际内存用量。

  1. 报告 total 是静态段尺寸之和，不是文件长度。1
  2. 排除 PAGEZERO 后的 1,081,344 B 仍是静态尺寸。2
  3. 这四个程序没有运行，实际驻留内存保持未知。1

适用于原创四例Apple clang 17 / arm64静态观察，未运行程序

1

zero-1m 的数字分别从哪里来？

图的结构
  • zero-1m 的三种读数 input
  • 文件长度 16,888 B file
  • size -m total 4,296,048,640 B total
  • 实际驻留内存 未运行 · 未知 resident
  • __PAGEZERO 4,294,967,296 B guard
  • 其余三个段 1,081,344 B permitted
  • input → file · 文件字节
  • input → total · 静态报告
  • input → resident · 未运行
  • total → guard · maxprot = 0
  • total → permitted · maxprot ≠ 0

图中的分支是阅读口径，不是执行顺序或调用关系。只有报告 total 的两个子项在同一口径内相加；文件长度与运行时内存不能加入这个合计。1

  1. 先看文件长度 ↗

    16,888 B 是整个文件的逻辑长度，不是 payload 的大小，也不是磁盘已分配块数。

  2. 再读报告 total ↗

    size -m 累加段的 vmsize；此例连 4 GiB 的 PAGEZERO 都计入。

  3. 分出不可访问区域 ↗

    PAGEZERO 的 maxprot 与 initprot 均为 0，filesize 也为 0；Bloaty 源码不将此类区域计入 VM。

  4. 其余尺寸仍是静态信息 ↗

    三个 maxprot 非零的段合计 1,081,344 B。这不是运行时 RSS。

  5. 保留尚未测量的结论 ↗

    没有执行这四个程序，不能从文件或段尺寸推出实际驻留内存。

改变数组长度或初值，会发生什么？

四个输入均为原创三行 C 程序，仅改变数组长度和首个初值；用同一 Apple clang 编译。数值来自本机静态输出，两次独立构建一致。所有字节列单位为 B。1

零初始化数组变大，文件可以不变大

两份 zero 输入的文件长度都为 16,888 B，而 __DATA 的静态 vmsize 从 16,384 B 增至 1,048,576 B。非零初值的 data 对照则有文件数据；其中还包含段对齐与元数据开销。

4

Bloaty 提供的阅读边界

固定源码对 maxprot 为 NONE 的段只记文件范围；零填充节的文件大小设为 0。本机零初始化数据实际节名为 __common、类型为 S_ZEROFILL，不能只靠节名猜测是否占文件字节。2

Bloaty 的归属图还有回退标签与启发式分配；每个字节归给一个标签，不代表删除这个符号就能省下相同字节。该边界与既有 retained-size 阅读有关，本实验没有再做符号归属或删除收益推算。3

如何复核与继续测量？

仅验证这四个 arm64 Mach-O 文件。没有执行 Bloaty、没有通用二进制导入器、没有人类阅读效率测量。所有原始流和两次构建的文件哈希保留在观察包。
