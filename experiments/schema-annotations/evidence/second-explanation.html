baz 写进 schema，为什么仍被拒绝？

长图

答

结论

案例 2 中，baz 分支失败，不能贡献属性覆盖。anyOf 成功，但 baz 仍未覆盖，整体校验失败。

  1. 写在 schema 中，不等于被成功分支覆盖。1
  2. 两个分支同时成功时，anyOf 汇总两者的覆盖。1
  3. 主错误只指出遗漏属性；分支原因来自额外的独立检查。2

适用于2020-12 固定四例Ajv 8.20.0独立检查非执行轨迹

1

案例 2 的覆盖如何汇总？

图的结构
  • 根属性 foo root-foo
  • bar 分支成功 bar-ok
  • baz 分支失败 baz-no
  • quux 分支失败 quux-no
  • 覆盖 foo、bar covered
  • 不贡献覆盖 discarded
  • baz 未覆盖 remaining
  • root-foo → covered · foo
  • bar-ok → covered · bar
  • baz-no → discarded · const 不符
  • quux-no → discarded · 属性缺失
  • covered → remaining · 缺少 baz
  • discarded → remaining · baz 未贡献

输入为 foo=foo、bar=bar、baz=not-baz。图表示依据规范与独立检查得出的覆盖关系，不表示 Ajv 内部执行顺序。3

  1. bar 分支成功 ↗

    bar 等于要求的常量 bar，分支通过；anyOf 已满足。

  2. baz 分支失败 ↗

    baz 是 not-baz，不等于常量 baz；该分支不能贡献覆盖。

  3. quux 分支失败 ↗

    输入没有 quux，required 失败；缺失属性本身不会成为多余属性。

  4. 覆盖 foo、bar ↗

    根 properties 覆盖 foo，成功分支覆盖 bar。

  5. baz 未覆盖 ↗

    输入属性减去覆盖集合，余下 baz；unevaluatedProperties 为 false，因此整体失败。

主诊断没有说出的原因是什么？

案例 2 的完整主错误如下。开启 allErrors 后仍是这个结果。2

独立校验 #/anyOf/1 得到 const 失败，要求值为 baz。这是额外诊断，不能冒充主校验输出或执行轨迹。完整输入、schema 和两种配置的原始记录保留在 观察包2。

anyOf 不是只保留第一个成功分支

案例 3 同时成功的 bar、baz 分支都贡献覆盖。把它改读成 oneOf 或遇到第一次成功就停止收集，会误判此例。
